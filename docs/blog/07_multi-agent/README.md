# 멀티에이전트란 무엇일까? — 역할을 나누고, 결과를 모아 함께 검토하기

![cover](cover.png)

> 작성: 이건규 · 게시: 2026-10-19 · [가짜연구소 원문](https://pseudo-lab.com/blog/d3f051fa-92c6-41be-b494-260e72916233)

자료를 읽고, 코드를 실행하고, 글을 쓰고, 검토까지 해야 하는 일을 AI 하나에게 모두 맡기면 어떤 일이 생길까요?

짧은 작업은 하나로 충분할 수 있습니다. 하지만 역할과 확인 기준이 다른 작업은 나누어 처리하는 구조를 생각해볼 수 있습니다. 이것이 **멀티에이전트(multi-agent)**의 출발점입니다.

## 1. 멀티에이전트는 무엇인가요?

**여러 에이전트에게 역할과 작업을 나누고, 그 결과를 전달·조정·통합하는 방식**입니다.

예를 들어 문서 검토 작업이라면 다음처럼 나눌 수 있습니다.

| 역할 | 맡은 일 | 내놓는 결과 |
| --- | --- | --- |
| 자료 확인 담당 | 원문과 출처를 읽음 | 위치와 근거 목록 |
| 계산 확인 담당 | 수치와 집계 조건을 대조함 | 계산·관측값과 불일치 |
| 통합 담당 | 결과를 대조하고 최종 답을 구성함 | 확인된 결론과 미확인 사항 |

각 역할이 무엇을 입력받고 무엇을 반환할지 정해야 합니다. 여러 에이전트를 쓰는 경우에도 최종 답을 누가 책임질지 명확히 해야 합니다. [공식 OpenAI 협업 구조 안내](https://developers.openai.com/api/docs/guides/agents/orchestration)

> ‘여러 AI가 모두 맞다고 했다’가 곧 사실의 증거는 아닙니다. 최종 판단은 원문·실행 결과 등 실제 근거와 연결해야 합니다.

## 2. 여러 모델을 쓰는 것과 같은 뜻인가요?

둘은 구분해서 생각하면 좋습니다.

| 구분 | 의미 |
| --- | --- |
| 여러 모델 사용 | 서로 다른 모델을 작업에 활용 |
| 여러 에이전트 사용 | 역할·지시·작업 상태를 구분한 작업자들을 구성 |
| 여러 채팅 사용 | 대화 공간을 나누어 실행 |

같은 모델을 서로 다른 역할의 에이전트로 구성할 수도 있습니다. 반대로 모델 셋에게 같은 질문을 하고 답을 읽기만 하는 것은 여러 모델 비교에 가깝고, 역할 간 인계·통합까지 설계한 협업과는 다릅니다.

채팅을 세 개 열었다고 자동으로 서로 대화하거나 같은 파일을 공유하는 것은 아닙니다. 어떤 자료를 누구에게 전달할지 사람이나 실행 시스템이 관리해야 합니다.

## 3. 작업을 나누는 기본 형태

### 순서대로 전달하기

```text
명세 만들기 → 구현·실행 → 결과 검토 → 최종 통합
```

앞 단계의 결과가 있어야 다음 단계가 가능한 경우입니다. 실행하지 않은 결과를 기다리는 단계에서 숫자를 추측해 채우면 안 됩니다.

### 나누어 살펴본 뒤 모으기

```text
              ┌─ 원문·출처 확인 ─┐
공통 입력 ────┤                  ├─ 결과 대조·통합
              └─ 숫자·계산 확인 ─┘
```

서로 독립적으로 살펴볼 수 있는 일을 나눕니다. 각자 같은 버전의 자료를 받았는지 확인해야 합니다. 독립 작업은 병렬로 처리할 수 있지만, 같은 파일을 수정하는 작업은 조정이 필요합니다. [공식 OpenAI 멀티에이전트 안내](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)

### 작성하고 다른 역할이 검토하기

```text
초안 작성 → 근거 기반 검토 → 필요한 부분 수정 → 사람 확인
```

검토자는 무조건 반대하거나 무조건 동의하는 역할이 아닙니다. 어떤 주장에 어떤 근거가 있는지 확인하고, 정상 내용은 보존하며, 자료가 부족한 부분을 표시합니다.

## 4. ‘총괄이 모으기’와 ‘담당에게 넘기기’

두 방식은 최종 답을 누가 맡는지에서 차이가 납니다.

| 방식 | 동작 | 예시 |
| --- | --- | --- |
| 총괄이 결과를 모음 | 전문 담당은 부분 결과를 반환하고 총괄이 최종 답을 작성 | 계산 담당과 문헌 담당의 결과를 종합 |
| 담당에게 제어를 넘김 | 해당 전문 담당이 이후 대화나 답변을 이어받음 | 접수 담당이 전문 분야 담당에게 넘김 |

공식 SDK 문서에서는 각각 agents as tools 방식과 handoff 방식으로 설명합니다. 제품과 구현에 따라 실제 연결 방법은 다릅니다. [공식 OpenAI 역할 인계 안내](https://developers.openai.com/api/docs/guides/agents/orchestration)

처음에는 ‘누가 최종 답을 쓰는가?’만 명확히 해도 구조를 이해하는 데 도움이 됩니다.

## 5. 나누기 전에 다섯 가지를 정합니다

1. **목표:** 전체 작업이 끝났을 때 무엇이 있어야 하나요?
2. **분담:** 각 역할의 질문과 범위는 무엇인가요?
3. **입력·출력:** 어떤 버전을 받고 어떤 형식으로 돌려주나요?
4. **통합:** 결과가 충돌하거나 누락되면 누가 해결하나요?
5. **종료:** 언제 충분하다고 보고 멈추나요?

‘A는 똑똑한 전문가, B는 더 엄격한 전문가’보다 ‘A는 원문 위치, B는 분모와 계산을 확인한다’처럼 관측 가능한 일을 나누는 편이 분담을 확인하기 쉽습니다.

## 6. 가장 중요한 것은 인계입니다

결과를 “다 했어요”라고만 넘기면 다음 역할은 무엇을 믿어야 할지 알기 어렵습니다.

아래 양식은 사람이 채팅 사이에서 전달할 때도 사용할 수 있습니다.

```text
작업 ID:
받은 자료와 버전:
내가 맡은 범위:
실제로 확인한 파일·근거:
관측한 결과:
판단과 이유:
확인하지 못한 부분:
다음 담당에게 필요한 자료와 행동:
```

파일을 수정했다면 바뀐 경로와 변경 이유도 함께 남깁니다. 원자료·초안·검토 결과·최종본을 구분하면 어느 단계에서 문제가 생겼는지 추적하기 쉽습니다.

## 7. 여러 에이전트를 쓰면 무조건 좋아지나요?

그렇지는 않습니다. 다음은 설계할 때 확인할 질문입니다.

| 기대하는 이점 | 함께 확인할 점 |
| --- | --- |
| 역할에 집중할 수 있음 | 역할이 겹쳐 같은 일을 반복하지 않는가 |
| 독립 작업을 병렬로 진행 | 실제로 서로 기다리지 않고 진행할 수 있는가 |
| 다른 관점으로 검토 | 앞 답을 그대로 따라가거나 같은 오류를 반복하지 않는가 |
| 부분 작업을 나누어 관리 | 인계 누락과 통합 비용이 더 커지지 않는가 |

작은 일을 여러 단계로 쪼개면 호출·대기·통합 작업만 늘 수 있습니다. 처음에는 하나로 실행해보고, 실제로 역할 분리가 필요한 부분부터 추가하세요.

결과를 비교할 때는 정답률만이 아니라 근거 정확성, 정상 오탐, 빠진 작업, 실제 걸린 시간과 확인 가능한 비용도 함께 봅니다. 여러 에이전트가 항상 빠르거나 정확하다고 가정하지 않습니다.

## 8. 처음 해볼 수 있는 수동 실습

코드로 연결하기 전에 새 채팅 세 개를 이용해 분담과 인계를 경험할 수 있습니다. 사람이 자료를 전달하는 협업 실습이며, 자동 통신이나 병렬 실행이 설정되는 것은 아닙니다.

### 공통 입력

```text
사례 ID: MULTI-01
주장: 계획한 대상자 10명 전원에게 결과를 제공했다.
근거 E01: 8명에게 결과를 제공했고 2명은 보류했다.
```

### 채팅 A: 원문·범위 확인

```text
제공된 주장과 E01만 읽어라.
주장이 말하는 대상과 실제 근거가 말하는 대상을 비교하라.
근거의 짧은 인용, 관측한 차이, 미확인 사항을 반환하라.
없는 자료를 만들거나 다른 담당의 결과를 추측하지 마라.
```

### 채팅 B: 숫자 확인

```text
제공된 E01에서 계획·제공·보류 인원을 정리하라.
제공 비율을 계산하고 분모와 계산식을 함께 적어라.
제공하지 않은 2명의 결과를 만들어 넣지 마라.
```

A와 B에게 공통 입력을 각각 제공합니다. 처음의 관점을 나눠 보고 싶다면 A의 답을 B의 입력에 먼저 섞지 않습니다. 그렇다고 모델의 사전 지식이나 오류가 독립적이라는 뜻은 아닙니다.

### 채팅 C: 통합

```text
원래 주장과 E01, 그리고 A·B의 실제 결과를 받는다.
다수결하지 말고 각 결과가 원래 근거와 맞는지 확인하라.
최종 판정, 근거, 이유, 최소 수정안과 남은 불확실성을 적어라.
없는 담당 결과를 추측해 채우지 말고 누락을 표시하라.
```

C에게는 공통 입력과 A·B의 실제 응답을 함께 전달합니다. **기대 결과는 전원 제공 주장을 받아들이지 않고, 8명 제공·2명 보류와 제공 비율 80%를 구분하는 것**입니다. 이는 설명용 기대값이며 실제 모델 실행 결과는 아닙니다.

## 9. 실행 후에는 무엇을 확인하나요?

| 확인 항목 | 질문 |
| --- | --- |
| 역할 수행 | 각 역할이 맡은 확인을 실제로 했나요? |
| 인계 | 원문·근거·버전과 실제 결과를 전달했나요? |
| 통합 | 충돌을 감추거나 다수결로 대신하지 않았나요? |
| 수정 | 원래 하지 않은 작업이나 수치를 추가하지 않았나요? |
| 효율 | 하나의 에이전트로 할 때보다 나누는 이유가 있었나요? |

하나로 실행한 경우와 비교하려면 같은 입력과 가능한 도구 조건을 맞추고, 여러 역할의 호출·대기·통합을 포함해 기록해야 합니다.

## 10. Falsify 제작에서는 어떻게 연결되나요?

Falsify에서는 정상 연구 명세·국문·인용, 코드·실험·Git, 영문·검토 자료 통합 등 역할을 나누어 제작했습니다. 역할별 폴더와 인계 파일을 사용했고, 사람이 자료를 전달하는 방식이 포함됐습니다.

이 사례를 “세 모델이 자동으로 서로 대화해서 모두 검증했다”는 뜻으로 소개하면 안 됩니다. 실제로 한 일과 남아 있는 검수를 구분해야 합니다. 여러 역할을 썼다는 사실 자체가 논문이나 정답 기준의 정확성을 보장하지도 않습니다.

## 자주 하는 오해

**“이름만 세 개 주면 서로 다른 에이전트인가요?”**

한 답변에서 세 역할을 흉내 내는 것과, 별도 작업 상태로 실제 실행·인계하는 구조는 구분해야 합니다.

**“모든 역할이 같은 파일을 수정해도 되나요?”**

동시 수정은 충돌이나 덮어쓰기를 일으킬 수 있습니다. 파일·담당 범위를 나누고 최종 반영 담당을 정하세요.

**“검토자는 정답만 알면 되나요?”**

실제 근거를 확인해야 합니다. 앞 담당의 결론만 받으면 잘못된 결론을 그대로 확대할 수 있습니다.

**“MCP가 여러 에이전트를 연결해주나요?”**

MCP는 도구·자료 연결에 쓰는 규약입니다. 어떤 에이전트에게 무엇을 맡기고 결과를 어떻게 통합할지는 별도의 협업·실행 설계가 필요합니다.

## 한 번 정리해보기

```text
전체 목표를 정한다.
역할별 질문과 입출력을 나눈다.
실제 근거와 관측값을 인계한다.
통합 담당이 결과를 대조한다.
사람이 최종 결과와 남은 불확실성을 확인한다.
```

처음에는 역할 두 개와 통합 담당 하나로 작은 일을 해보세요. 여러 AI를 부르는 것보다 **어떤 일을 나누고, 무엇을 전달하고, 누가 검증하는지**를 분명히 하는 것이 출발점입니다.
