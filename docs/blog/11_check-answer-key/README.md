# 정답표 점검하기 — 오탐이 정답지 오류일 때

![cover](cover.png)

> 작성: 이건규 · 게시: 2026-11-02 · 가짜연구소 Falsify 자료 탭


## 이 글은 AI로 초안을 작성하고 사람이 검토했습니다!

탐지기의 정밀도가 21.1%라면 나쁜 탐지기일까요?

Falsify 1회차에서 논문에 결함 8개를 심었습니다. 찾는 쪽은 8개를 모두 찾았고, 지적을 모두 38건 제출했습니다. 정답지에 있는 것만 정답으로 세면 정밀도는 8/38 = 21.1%입니다. 그런데 38건 중 근거가 틀린 지적은 한 건도 없었습니다.

나머지 30건은 무엇이었을까요? 이번 글에서는 AI의 판정과 정답표가 어긋날 때, **틀린 쪽이 정답표일 수도 있다**는 가능성을 점검하는 방법을 다룹니다. 이번에도 새 채팅과 기록표만으로 실습합니다.

> 이 글의 Falsify 수치는 김가경 님의 「탐지기를 측정한 4주와 빌런나이트 발표」(2026.10.29)에서 가져왔습니다.

## 1. 정답표와 오탐

**정답표**는 무엇이 정답인지 미리 적어 둔 표입니다. Falsify에서는 결함을 심는 Red 쪽이 정답표를 따로 작성하고, 채점은 찾는 세션이 끝난 뒤에 합니다.

**오탐**은 탐지기가 "문제 있다"고 했는데 정답표에는 없는 지적입니다.

오탐은 정답표를 기준으로 정해집니다. 정답표가 빠뜨린 것이 있거나 틀린 것이 있으면, 탐지기가 맞게 지적해도 오탐으로 셉니다.

## 2. 정밀도는 무엇을 정답으로 세느냐에 따라 달라집니다

Falsify 1회차의 38건을 나눠 보면 이렇습니다.

| 지적의 종류 | 건수 | 정답지 기준 |
|---|---|---|
| 심은 결함 | 8 | 정답 |
| 원본 논문에 원래 있던 어긋남 | 19 | 오탐 |
| 주장의 수위 지적 (결론이 근거보다 세다는 판단) | 11 | 오탐 |
| 합계 | 38 | 정밀도 8/38 = 21.1% |

19건은 결함을 심기 전부터 원본 논문에 있던 어긋남이었습니다. 탐지기가 찾은 것은 실제 문제였지만, 정답지에 없으니 오탐으로 세었습니다.

그래서 원본에 어긋남이 있으면 **탐지기가 잘 찾을수록 정밀도가 오히려 떨어집니다.** 2회차(결함 5개)에서도 같은 현상이 나왔습니다. 그래서 Falsify 팀은 탐지기보다 **원본의 품질부터 측정해야 한다**는 결론을 냈습니다.

정밀도 숫자 하나를 보여줄 때는 반드시 **무엇을 정답으로 셌는지**를 함께 밝혀야 합니다.

## 3. 오탐을 네 가지로 나눠 봅니다

정답표에 없는 지적이 나오면 바로 "AI가 틀렸다"고 적지 말고, 먼저 분류해 보세요.

| 분류 | 의미 | 할 일 |
|---|---|---|
| 진짜 오탐 | 근거를 잘못 읽었거나 없는 문제를 만듦 | 탐지기 쪽 실패로 기록 |
| 원본의 기존 문제 | 심지 않았지만 원본에 실제로 있던 문제 | 원본 품질 기록에 추가 |
| 수위·해석 지적 | 사실은 맞지만 결론이 근거보다 세다는 판단 | 별도 범주로 따로 집계 |
| 정답표 오류 | 정답표 자체가 틀렸음 | 정답표를 고치고 버전을 올림 |

분류는 사람이 원문을 보고 합니다. 탐지기에게 "네 지적이 맞니?"라고 묻는 것으로는 정할 수 없습니다.

## 4. 실제로 정답지가 틀렸던 사례

Falsify에서 결함을 심을 때, 히스톤 표지 두 개가 바뀐 것을 단순한 오타 수준으로 보고 정답지에 적은 경우가 있었습니다. 그런데 두 표지는 하나는 전사를 억제하고 다른 하나는 활성화하는, **뜻이 반대인 표지**였습니다.

이 오류는 탐지 결과의 '오탐'을 다시 보는 과정에서, 분야를 아는 참가자가 발견했습니다. 팀이 실무 권고로 정리한 문장이 이것입니다.

> 오탐이 나오면 탐지기보다 정답지를 먼저 의심합니다.

그럴듯하게 틀린 결함을 심으려면 분야를 깊이 알아야 하고, 정답지를 검토할 때도 마찬가지입니다. 결함을 심는 일이 찾는 일보다 어렵다는 것도 4주 동안 팀이 배운 것 중 하나입니다.

## 5. 심는 쪽과 찾는 쪽이 비슷하면

Falsify 팀이 아직 풀지 못한 문제도 하나 있습니다. 결함 후보를 AI에게 받아 사람이 골랐고, 찾는 데에도 같은 계열의 도구를 썼습니다. **비슷한 편향을 가진 도구끼리 서로를 채점한 셈**이라 결과를 그대로 믿기 어렵습니다.

정답표를 만들 때 AI의 도움을 받았다면, 그 사실을 정답표에 적어 두세요. 나중에 점수를 해석할 때 필요합니다.

## 준비물과 이번에 만들 것

- ChatGPT 또는 Claude에서 새 채팅을 열 수 있는 환경
- 메모장이나 Markdown 편집기
- 기록표

이번 목표는 **일부러 오류를 하나 넣은 정답표로 채점해 보고, 충돌한 항목을 원문으로 되짚어 정답표를 고치는 것**입니다.

## STEP 1. 정답표 형식을 정합니다

```
항목 ID:
대상 문장:
근거 ID:
기대 판정: 맞음 / 아님 / 확인 필요
기대 판정의 이유:
작성자:
AI 도움 여부: 예 / 아니요
정답표 버전:
```

'기대 판정의 이유' 칸이 있어야 나중에 정답표가 틀렸는지 확인할 수 있습니다. 판정만 적힌 정답표는 고칠 근거도 남지 않습니다.

## STEP 2. 연습용 정답표를 만듭니다

공통 예제로 세 항목을 만듭니다. **K02에는 일부러 오류를 넣었습니다.**

```
근거 E01: 계획한 10명 중 8명에게 결과를 제공했고 2명은 보류했다.
```

| 항목 | 대상 문장 | 기대 판정 (v1) | 이유 |
|---|---|---|---|
| K01 | 계획한 10명 중 8명에게 결과를 제공했다. | 맞음 | E01과 일치 |
| K02 | 계획한 10명 전원에게 결과를 제공했다. | 맞음 | (작성 실수) |
| K03 | 결과를 받은 8명 모두 만족했다. | 확인 필요 | 만족도 자료 없음 |

이 정답표는 AI에게 보여주지 않습니다.

## STEP 3. 정답표 없이 판정을 받습니다

하네스 글 STEP 2의 검토 도우미 지시를 쓰고, 항목마다 새 채팅에서 대상 문장과 E01만 줍니다.

| 항목 | 기대 판정 (v1) | AI 판정 | 일치 |
|---|---|---|---|
| K01 | 맞음 | | |
| K02 | 맞음 | | |
| K03 | 확인 필요 | | |

판정이 흔들릴 수 있으니, 2편에서 한 것처럼 항목마다 두세 번 반복해 두면 더 좋습니다.

## STEP 4. 충돌한 항목을 모읍니다

기대 판정과 AI 판정이 다른 항목만 따로 모읍니다. 이 단계에서는 아직 누가 맞는지 정하지 않습니다.

```
충돌 항목: K02
정답표: 맞음
AI 판정: (실제 결과 기록)
AI가 인용한 근거: (원문 그대로)
```

## STEP 5. AI에게 이의 제기서를 쓰게 합니다

새 채팅에서 충돌 항목 하나를 주고 이의 제기서를 쓰게 합니다.

```
아래 항목에서 정답표와 검토 결과가 다르다.
어느 쪽이 맞는지 결론 내리지 말고, 이의 제기서를 아래 형식으로 써라.
제공한 근거만 쓰고, 근거에 없는 내용은 만들지 마라.

- 항목 ID:
- 정답표의 판정과 이유:
- 검토 결과의 판정과 이유:
- 근거 원문 인용:
- 정답표를 고쳐야 한다면 그 이유:
- 검토 결과가 틀렸다면 그 이유:
- 이 근거만으로 결론 낼 수 없는 부분:

근거: (E01)
대상 문장: (문장)
정답표: (판정과 이유)
검토 결과: (판정과 인용)
```

AI에게 판결을 맡기지 않고 **양쪽 근거를 정리하게** 하는 것이 요점입니다. 결정은 다음 단계에서 사람이 합니다.

## STEP 6. 사람이 원문을 보고 분류합니다

이의 제기서를 읽고, 근거 원문을 직접 확인한 뒤 3장의 네 분류 중 하나로 정합니다.

| 항목 | 분류 | 결정 | 이유 |
|---|---|---|---|
| K02 | 정답표 오류 | 기대 판정 '맞음' → '아님' | E01은 8명 제공·2명 보류 |

K02의 기대 결과는 정답표 오류입니다. 설명용 기대값이며 실제 모델 실행 결과는 아닙니다.

## STEP 7. 정답표 버전을 올리고 변경 이유를 남깁니다

```
정답표 v2 (변경 1건)
- K02: 맞음 → 아님
  이유: E01과 충돌. v1 작성 시 실수.
  발견 경로: 검토 결과와의 충돌 → 이의 제기서 → 원문 확인
```

정답표를 조용히 고치면 v1으로 계산한 점수와 v2로 계산한 점수가 섞입니다. 점수를 보고할 때는 **어느 버전의 정답표로 채점했는지**를 함께 적으세요.

## STEP 8. 무엇을 정답으로 셌는지 밝힙니다

결과를 공유할 때 아래처럼 쓰면 읽는 사람이 숫자를 오해하지 않습니다.

| 오해하기 쉬운 보고 | 범위를 밝힌 보고 |
|---|---|
| 정밀도 21.1% | 정답지 v1에 있는 심은 결함만 정답으로 셌을 때 8/38. 나머지 30건 중 19건은 원본의 기존 어긋남, 11건은 수위 지적. |
| AI가 1건 틀렸다 | 충돌 1건. 원문 확인 결과 정답표 오류로 분류해 v2에서 수정. |

## STEP 9. 사람이 볼 자리를 정해 둡니다

이 시리즈에서 사람이 판단하는 자리는 계속 나왔습니다. 대조군의 '실제로' 칸을 적는 사람, 판정이 갈린 항목을 보는 사람, 충돌 항목을 분류하는 사람입니다.

작업을 시작하기 전에 아래 정도는 정해 두세요.

- 정답표와 판정이 충돌하면 누가 원문을 확인하는가
- 분야 지식이 필요한 항목은 누구에게 묻는가
- 결론이 근거보다 센 지적(수위 지적)은 어떻게 집계하는가

AI 검토를 붙여도 이 자리는 사라지지 않습니다. 오히려 어디에 사람이 있어야 하는지가 더 분명해집니다.

## 자주 헷갈리는 질문

**정답표를 자주 고치면 결과를 조작하는 것 아닌가요?**
변경 이유와 버전을 남기지 않고 고치면 그렇게 보일 수 있습니다. 그래서 STEP 7처럼 무엇을, 왜, 어떤 경로로 고쳤는지 기록합니다. 탐지 결과에 맞춰 정답표를 고치는 것이 아니라 **원문에 맞춰** 고칩니다.

**수위 지적은 정답인가요, 오탐인가요?**
정해진 답은 없습니다. 연구 목적에 따라 다릅니다. 중요한 것은 따로 집계해서, 읽는 사람이 어떤 기준으로 셌는지 알 수 있게 하는 것입니다.

**AI가 만든 정답표는 믿을 수 있나요?**
사람이 만든 정답표도 틀립니다. 누가, 어떤 도움을 받아 만들었는지 적고, 충돌이 나오면 원문으로 확인하는 절차가 있으면 됩니다.

## Falsify 실습에서는 이렇게 써보세요

- 정답표에 '기대 판정의 이유'와 'AI 도움 여부' 칸을 넣어 주세요.
- 오탐으로 분류된 지적은 바로 버리지 말고 네 분류 중 어디인지 표시해 주세요.
- 정답표를 고쳤다면 버전과 변경 이유를 공동 기록표에 남겨 주세요.

## 완성 체크리스트

- [ ] 정답표에 판정의 이유를 적었는가
- [ ] 정답표를 AI 입력과 분리했는가
- [ ] 충돌 항목을 모은 뒤 바로 결론 내리지 않았는가
- [ ] 이의 제기서로 양쪽 근거를 정리했는가
- [ ] 사람이 원문을 보고 분류했는가
- [ ] 정답표 버전과 변경 이유를 남겼는가
- [ ] 점수를 보고할 때 무엇을 정답으로 셌는지 밝혔는가

## 마무리

세 편에 걸쳐 AI 검토 결과를 믿기 전에 확인할 것들을 다뤘습니다. 참인 문장도 함께 넣어 보는 대조군, 같은 질문을 여러 번 묻는 반복, 그리고 정답표 자체에 대한 점검입니다.

세 가지 모두 AI를 의심하자는 이야기보다는, 내가 가진 숫자가 무엇을 말해 주는지 알기 위한 점검입니다. 오탐 속에서 정답표 오류를 찾은 경험이 있다면 공유해 주세요.
