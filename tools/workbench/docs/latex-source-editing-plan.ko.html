LaTeX 소스 기반 논문 편집 구현계획

본문·수식·윗첨자·각주를 소스 구조로 편집하고, 같은 조판 환경에서 변경 전·후 PDF를 만든다.
사용자는 현재처럼 논문을 넣고, 미리보기에서 수정하고, PDF를 받는다. LaTeX 코드와 컴파일 설정은 고급 기능에 둔다.

이 문서는 구현 착수 전 작성한 계획이다. 이후 구현·검증 결과와 남은 범위는 현재 구현 상태에서 확인한다. 아래 작업 ID는 계획서 내부 ID이며 WorkBite Task ID가 아니다.

1. 결정과 범위

원본 LaTeX 프로젝트가 있으면 소스 편집을 우선 사용한다. PDF만 있으면 현재의 원본 보존 편집을 계속 제공하면서, 편집용 LaTeX 재구성 경로를 별도로 추가한다. 원본 PDF의 좌표를 고치는 방식과 문서 전체를 다시 컴파일하는 방식은 세션별로 구분한다.

경로입력과 처리완료할 결과
원본 소스 경로: 먼저 구현.tex 단일 파일 또는 소스 ZIP. 그림, .bib/.bbl, .cls/.sty, 필요한 글꼴을 프로젝트로 읽고 컴파일본문·윗첨자·각주·인용 편집, 자동 미리보기, PDF·소스 ZIP 다운로드, BLUE 전달
PDF 재구성 경로: 다음 구현PDF의 본문·수식·표·그림·각주·참고문헌을 구조화하고 편집용 LaTeX 프로젝트 생성무수정 재구성본 확인 후 같은 소스 경로에서 편집. 재구성 차이와 공격 변경을 따로 기록
기존 PDF 편집 경로현재 paragraph/table/image 편집 엔진 사용alpha.33의 짧은 수정, 원본 보존, 독립 BLUE 흐름 유지

첫 버전은 기존 표·그림을 포함한 소스 프로젝트를 보존해서 컴파일한다. 그림 생성·교체 자동화, 모든 출판사 템플릿 지원, 임의 병합 표의 시각적 편집은 이후 확장한다. 소스 경로를 추가하면서 기존 PDF 편집기의 혼합 서식 오류도 작은 별도 수정으로 다룬다. LaTeX 전환 완료를 기다리게 하지 않는다.

2. 기존 구현과 OSS 재사용

프로젝트에서 확인한 사실

  • feat/latex-red-engine의 latex_red_harness.py는 추출 텍스트에서 결정적 변경 후보를 만든다. LaTeX 프로젝트를 파싱하거나 컴파일하는 엔진이 아니다.
  • 현재 document-import.js는 .tex를 텍스트로 읽는다. 매크로·참조를 해석하고 PDF를 조판하는 단계가 필요하다.

  • 기존 편집 스냅샷은 허용 필드를 엄격히 검사한다. 새 소스 좌표를 기존 v1 객체에 임의로 넣지 않고, 버전이 있는 별도 source session과 명시적인 호환 어댑터를 둔다.

3. 사용 흐름

소스 프로젝트가 있을 때

  1. 기존 입력 영역에 소스 ZIP 또는 .tex를 넣는다. PDF와 소스를 함께 넣을 수도 있다.
  2. 앱이 루트 문서를 찾아 기준 PDF를 만든다. 후보가 여러 개일 때만 대표 파일 하나를 고르게 한다. 빠진 파일은 파일명과 추가 버튼으로 표시한다.
  3. 기준 PDF 위의 문장·수식·번호를 클릭해 수정한다. 외부 AI의 Before/After 응답을 가져오는 흐름도 유지한다.
  4. 편집은 즉시 반영하고 재컴파일 결과로 미리보기를 갱신한다. 기존 페이지 넘김과 원문·변경본 하이라이트를 사용한다.
  5. 현재 변경이 반영된 PDF를 바로 받거나 BLUE에 전달한다. 소스 ZIP과 상세 컴파일 로그는 펼친 메뉴에서 받는다.

PDF만 있을 때

  1. PDF를 넣으면 기존 편집기를 바로 사용할 수 있다.
  2. 소스 재조판을 선택하면 편집용 소스를 재구성하고, 원본 PDF와 무수정 재구성본을 나란히 보여준다.
  3. 누락·오인식된 본문, 수식, 표, 그림이 있으면 해당 위치에서 바로 보정한다. 확인한 기준본을 이후 변경의 출발점으로 고정한다.
  4. 그 뒤의 편집·AI 응답·다운로드·BLUE 전달은 소스 프로젝트와 같은 흐름을 쓴다.

UI는 공항 디자인, RED·BLUE·검수의 독립 진입점을 유지한다. 기본 화면에 AST, 엔진, manifest, 호출 예산 같은 항목을 늘리지 않는다. 소스 코드, 컴파일 엔진 선택, 패키지 로그와 원본 비교 상세만 고급 기능으로 접는다. 새 기능을 쓰기 위해 PC 연결이나 모델 계정을 요구하지 않는다.

4. 데이터와 편집 계약

객체필수 의미

SourceNode / SourceAnchor본문·수식·각주·인용·그림·표의 노드 ID, source file과 소스 범위, 표시 텍스트와 역매핑, 프로젝트 해시·revision. 파일 바이트와 JS UTF-16 오프셋의 변환 규칙을 계약에서 고정

BaselineArtifact공격을 넣기 전 PDF와 소스 상태, 원본/재구성 출처, 복원 차이, 사용자 보정 기록. RED 변경 이력과 분리

생성 키에는 projectHash + 활성 변경 + 엔진/패키지/글꼴 manifest + 출력 설정 + baselineId를 포함한다. 숫자 revision만으로 동일 결과를 판단하지 않는다. 원본 파일은 그대로 두고 변경 patch를 적용해 작업본을 만든다. 파일 전체를 AST printer로 다시 쓰지 않아 주석·매크로·사용자 형식을 보존한다.

본문·수식·윗첨자

  • LaTeX 매크로 인수와 수식 환경을 구분한다. 일반 텍스트 입력의 % $ & # _ { } 는 맥락에 맞춰 escape한다. LaTeX 코드를 직접 넣는 동작은 고급 편집에서 명시적으로 선택한다.
  • 문장을 통째로 받아도 실제 바뀐 source node와 문자 범위를 계산한다. 그대로인 윗첨자·강조·인용 매크로는 그대로 남긴다.
  • 본문 안의 \textsuperscript{62}, 수식의 x^{n+1}를 각각 편집한다. 혼합 이탤릭·아래첨자·색상도 구조와 속성을 유지한다.
  • SyncTeX로 PDF 위치에서 소스 파일·줄을 찾고, 노드와 표시 텍스트를 대조해 문자 범위를 좁힌다. SyncTeX 결과를 곧바로 정확한 문자 위치라고 간주하지 않는다. 한 소스가 여러 위치에 렌더링되는 매크로는 호출부와 정의부를 구분한다.

각주·인용의 두 가지 의미

사용자 의도처리유지할 것
각주 내용이나 인용 대상 변경\footnote{…}, \cite{key} 등 해당 소스 노드를 수정하고 정상 참조 계산템플릿의 번호 형식, 본문 연결, 참고문헌·각주 위치
보이는 번호만 의도적으로 변경선택한 참조의 표시값만 바꾸는 display-override 편집. 번호 클릭 후 숫자를 고치면 이 의도로 기록주변 번호·참고문헌·각주 본문을 자동으로 일괄 수정하지 않음. 자동 재번호 매김이 RED 결함을 없애지 않게 함

표시값 override는 별도의 템플릿 어댑터로 구현한다. \footnote를 단순한 문자열 치환으로 바꾸지 않는다. G0에서 기본 각주, 재사용 각주 표지, hyperref, natbib/biblatex 예제로 카운터·링크·주변 표기 보존을 증명한 구현을 선택한다. 임의의 사용자 매크로를 같은 규칙으로 처리한다고 가정하지 않는다.

외부 AI 응답

현재의 {changes:[{before,after,rationale,evidence}]}와 Markdown 응답을 계속 받는다. 사용자가 파일명·AST 경로·해시·LaTeX 문법을 새로 채우게 하지 않는다. 앱이 표시 텍스트에서 source anchor를 찾고, 복수 후보일 때만 해당 위치를 확인받는다. 기존 후보 체크·충돌 선택·원응답 보존 규칙을 유지한다.

5. 브라우저 컴파일과 자동 미리보기

  • LaTeX 컴파일은 전용 Worker에서 실행한다. 엔진과 패키지는 지연 로드하고 검증된 정적 자산을 재사용한다. 문서 본문과 사용자 그림·글꼴을 외부 컴파일 서버에 보내지 않는다.
  • 프로젝트 지정 엔진과 루트 설정을 먼저 따른다. 엔진 전환으로 글꼴·배치가 달라지는 경우에는 그 결과를 비교해 선택할 수 있게 한다. 동일 소스를 엔진마다 조용히 바꿔 실행하지 않는다.
  • BibTeX/Biber와 교차참조는 필요한 pass를 수행한다. unresolved reference, 누락 글꼴, overfull box, 실제 compile failure를 서로 구분한다.
  • 입력 중에는 편집창·커서·한글 조합을 유지한다. 최신 작업 하나만 남기고 컴파일 결과의 생성 키를 확인한다. 취소를 지원하지 않는 엔진은 Worker를 종료하고 새 프로젝트 상태로 다시 실행한다.
  • 패키지 캐시와 프로젝트 파일 캐시는 구분한다. 패키지는 고정 해시로 캐시하고, 사용자 파일은 기존 12시간 초안 동의와 보관 규칙을 적용한다.
  • 브라우저에서 시스템 글꼴을 자동 사용한다고 가정하지 않는다. 프로젝트 글꼴 또는 기존 글꼴 서비스에서 사용자가 제공한 바이트를 검증해 연결한다. 대체 글꼴을 선택했다면 컴파일 조건에 남긴다.
  • ZIP은 기존 fflate를 재사용하되 상대 경로·중복 파일·압축 해제량을 확인한다. TeX의 shell escape와 사용자 제공 JS handler는 기본 실행 경로에서 끈다. 프로젝트별 메모리 파일 시스템과 Worker를 분리한다.

다운로드는 클릭 시점의 편집을 반영한 PDF를 준비한 뒤 바로 실행한다. 생성 실패 시 마지막 성공본과 원본·작업 소스는 계속 받을 수 있고, 이전 PDF를 현재 변경이 적용된 파일로 표시하지 않는다. BLUE 전달도 같은 현재 artifact의 File/hash를 사용한다.

성능 검증 목표는 입력 반응 p95 100ms 이내다. 컴파일은 6쪽·36쪽 fixture에서 최초 로드와 캐시 후 전체 재컴파일의 시간·메모리를 따로 측정한다. 초기 목표는 캐시 후 6쪽 p95 3초, 36쪽 p95 10초이며 실측 후 문서에 결과를 기록한다. 현재 달성 수치가 아니다. LaTeX 컴파일이 실제로 전체 문서를 처리하면 이를 부분 컴파일로 표시하지 않는다.

6. PDF에서 편집용 소스 만들기

PDF 재구성은 원본 LaTeX 프로젝트 복원과 구분해 reconstructed-pdf로 기록한다. 현재 MuPDF/PDF.js와 구조화 문서 모델에서 텍스트·좌표·선·그림·글꼴 정보를 재사용하고, 인식이 필요한 부분에만 추가 추출기를 비교한다.

요소재구성 방법과 확인
본문·절·다단·참고문헌읽기 순서와 문단 경계를 복원하고 source node에 연결. 머리말·꼬리말을 본문으로 중복 삽입하지 않음
윗첨자·아래첨자·수식크기·baseline·문맥으로 후보를 만들고 원본 crop과 대조. 수식 구조가 불확실하면 보정 가능 상태로 남기고 원본 영역을 보존하는 선택 제공
그림·복합 패널벡터·이미지·clip·alpha·라벨을 함께 보존한 asset으로 가져옴. 기존 figure span/occurrence 처리 재사용. 그림 내부를 모두 본문 텍스트로 풀어버리지 않음
표셀·행·열·병합·각주 구조가 확인되면 LaTeX 표로 생성. 구조가 불명확한 영역은 원본 표현을 유지하며, 편집 가능 셀과 전체 표 이미지를 구분
각주와 인용표지와 실제 각주·참고문헌 항목의 연결을 기록. 표기 번호만으로 의미 연결을 단정하지 않음

재구성 전후에 텍스트 누락·숫자·수식·그림·표 수와 위치를 대조한다. 차이는 원본 PDF와 나란히 표시하고, 사용자 보정을 소스 노드에 반영한다. 문서 전체를 이미지 한 장씩 넣어 겉모습만 유지한 PDF는 편집용 소스 완료로 세지 않는다. 원본 그림·불확실한 영역을 이미지로 보존한 경우에는 그 영역의 편집 범위를 구분한다.

소스 재구성은 정답이나 논지를 교정하는 과정이 아니다. 이미 변조된 훈련용 입력의 모순도 유지한다. OCR·LLM이 의학·통계 내용을 정상화하거나 수치를 바꾼 차이는 재구성 오류로 분리한다.

7. RED/BLUE 실험과 출력 품질

원본 PDF, 기준 PDF, RED 변경 PDF를 별개의 artifact로 보존한다. 실제 소스가 있는 경우도 먼저 공격 없는 기준본을 컴파일해 템플릿·패키지·글꼴 차이를 확인한다. PDF 재구성 경로에서는 무수정 기준본과 공격본을 같은 환경에서 만든다. 원본 PDF와의 비교는 재구성 품질 평가에 사용한다.

  • BLUE에는 선택한 평가 조건의 PDF만 전달한다. LaTeX 프로젝트, 원본 비교, RED 계획, source map과 사람 판정은 전달하지 않는다.
  • 기준본의 무공격 BLUE 실행을 둘 수 있다. 재구성 때 생긴 결함과 RED가 주입한 결함을 별도 집계한다. 기준본을 만들었다고 BLUE가 원본을 함께 볼 수 있게 하지 않는다.
  • 자동 카운터·참조 처리로 RED가 의도한 불일치가 사라지면 변경 검증 실패로 기록한다. 자연스러운 조판과 과학적 결함의 보존을 각각 확인한다.
  • 하이라이트는 화면 비교 레이어로만 표시한다. 앱의 공격 표식·정답·변경 주석·소스 첨부를 BLUE용 PDF에 추가하지 않는다. 입력에 이미 있던 표식은 별도 원본 콘텐츠로 취급한다.
  • 페이지 수만으로 품질을 판정하지 않는다. 짧은 수정 fixture는 페이지·영역 보존을 검사하고, 긴 수정은 읽기 순서·누락·겹침·넘침·그림·표·각주 분리를 확인한다.

10. 적용 순서와 위험 대응

  1. 1차: G0 PoC와 공통 계약. 실제 원본 소스에서 윗첨자·각주·수식 편집과 브라우저 컴파일을 검증하고 사용할 OSS·자산을 확정한다.
  2. 2차: 원본 소스 프로젝트 입력, 클릭 편집, 외부 응답, 미리보기·다운로드·BLUE를 연결한다. 현재 PDF 경로는 유지하고 소스 프로젝트에만 새 엔진을 선택한다.
  3. 3차: 통합 회귀와 사용성 검수 후 버전·캐시를 함께 갱신한다. 실제 배포는 해당 실행 지시에 따라 진행한다.
  4. 4차: PDF→편집용 LaTeX 재구성과 기준본 보정·평가를 병렬 구현한다. 초기에는 재구성 결과를 사용자가 비교해 고르는 경로로 제공한다.

자동 번호 기능이 RED 결함을 정상화참조 의미와 표시 override를 별도 계약으로 유지. 주변 번호와 gold 변경의 보존을 테스트
대규모 엔진·패키지 때문에 첫 로드나 입력이 느려짐필요 엔진만 로드, 검증된 캐시·Worker·최신 작업 취소 사용. 최초/캐시 후 시간과 메모리를 분리 측정
UI·기록 스키마 변경이 기존 사용자 흐름을 깨뜨림조율자가 핵심 파일을 통합하고 legacy adapter 제공. 기존 artifact API와 독립 RED/BLUE/검수 회귀 유지

구현 시작 시 확정할 항목은 G0의 엔진·의존성 고정 SHA, 실제 필요한 TeX 자산 크기, 지원 템플릿 묶음, ZIP 한도와 source range 단위다. 새 데이터 계약과 fixture를 먼저 고정하고, 결과가 확인된 경로부터 제품에 연결한다.
